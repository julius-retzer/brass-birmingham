# Phase 01.1: Engine Rule Audit and Correctness Verification - Context

**Gathered:** 2026-03-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Systematically audit the existing game engine (gameStore.ts, action files, data files) against every rule in the Brass Birmingham rulebook. Produce a comprehensive rule checklist showing pass/fail/missing status with test evidence for each rule. This phase does NOT fix issues — it documents them for a subsequent fix phase.

</domain>

<decisions>
## Implementation Decisions

### Audit methodology
- **D-01:** Rule-by-rule comparison — walk through every rule in `ai-docs/brass-birmingham-rules.mdc`, check if the code implements it correctly
- **D-02:** Each rule gets a pass/fail/missing verdict with a pointer to the test file:line that proves it (or "no test" if missing)
- **D-03:** When the rulebook is ambiguous, look up clarifications online (BGG forums, FAQ, errata) before making a judgment

### Audit scope
- **D-04:** Includes data layer — audit `industryTiles.ts`, `board.ts`, `cards.ts`, `merchants.ts` against rulebook values (tile costs, connection graph, merchant bonuses)
- **D-05:** Includes engine logic — audit state machine, all 7 action implementations, scoring, era transitions, income, turn order
- **D-06:** Does NOT fix any issues found — produces a gap report only. Fixes happen in separate plans after audit

### Deliverable format
- **D-07:** Markdown rule checklist table: rule reference | implementation status (pass/fail/missing) | test evidence (file:line) | notes
- **D-08:** Machine-parseable format so gap closure plans can be generated from it
- **D-09:** Organized by rule area (actions, scoring, income, era transitions, data correctness, etc.)

### Claude's Discretion
- How to partition the rules doc into audit tasks (by section, by action type, etc.)
- Exact table column structure beyond the required fields
- Whether to create one monolithic report or multiple per-area reports
- Order of rule areas to audit

</decisions>
