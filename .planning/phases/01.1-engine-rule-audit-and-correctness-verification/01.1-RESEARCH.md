## Summary

This phase is an audit-only effort: systematically walk through every rule in the Brass Birmingham rulebook (`ai-docs/brass-birmingham-rules.mdc`) and compare it against the engine implementation (`gameStore.ts`, action files, data files). The deliverable is a structured markdown checklist with pass/fail/missing verdicts per rule, pointing to test evidence where it exists.

The codebase already has 426 passing tests across 28 test files covering actions, scoring, income, guards, integration, data validation, and edge cases. The engine is 2,997 lines in `gameStore.ts` plus supporting modules. The audit does NOT fix issues -- it produces a gap report that a subsequent phase consumes to generate fix plans.

**Primary recommendation:** Partition the rulebook into 6-8 auditable sections (setup/data, build, sell, network, develop/scout/loan/pass, scoring/era-transitions, resource-consumption, turn-flow), audit each section by reading the rule, locating the implementation, and checking existing test evidence. Produce machine-parseable markdown tables with consistent columns.

### Table Schema (Machine-Parseable)

Per D-07 and D-08, each section uses this consistent table format:

```markdown
| Rule Ref | Rule Description | Status | Test Evidence | Notes |
|----------|-----------------|--------|---------------|-------|
| BUILD-01 | Location card builds at named location even outside network | PASS | gameStore.build.test.ts:42 | |
| BUILD-02 | Wild Location cannot build at Farm Breweries | MISSING | -- | No test found |
| BUILD-03 | Canal era: max 1 industry per location per player | FAIL | gameStore.build.test.ts:88 | Guard missing for same-location check |
```

**Status values (exactly 3):**
- `PASS` -- Rule implemented correctly AND has test evidence
- `FAIL` -- Rule implemented but incorrectly, or test demonstrates wrong behavior
- `MISSING` -- Rule not implemented at all, or no test evidence to verify

**Rule Ref format:** `{AREA}-{NN}` where AREA is a short code (BUILD, NET, DEV, SELL, LOAN, SCOUT, PASS, SCORE, ERA, DATA, SETUP, TURN, COAL, IRON, BEER, INC).

### Anti-Patterns to Avoid
- **Vague verdicts:** "Probably works" is not a valid status. Either there is test evidence or there is not.
- **Fixing while auditing:** The temptation will be strong. Do NOT fix issues -- just document them (D-06).
- **Skipping ambiguous rules:** When rules are unclear, search BGG/FAQ first, then document the interpretation used (D-03).
- **Missing file:line references:** Every PASS must cite specific test evidence. "Tests exist" is insufficient.

## Common Pitfalls

### Pitfall 1: Confusing "tested" with "correct"
**What goes wrong:** A test passes but tests the wrong thing, or tests an incorrect interpretation of the rule.
**Why it happens:** Tests were written against developer understanding, not the rulebook.
**How to avoid:** For each rule, read the rulebook text first, THEN check if the test actually validates that specific rule.
**Warning signs:** Test name doesn't match the rule being audited; test assertions are weaker than the rule requires.

### Pitfall 2: Missing negative test coverage
**What goes wrong:** A rule says "you may NOT do X" but only positive cases are tested.
**Why it happens:** Positive paths are more natural to test.
**How to avoid:** For each prohibition rule, check for a test that attempts the forbidden action and verifies it fails.
**Warning signs:** Guard functions exist but have no test that triggers them.

### Pitfall 3: Data value drift
**What goes wrong:** Tile costs, connection lists, or merchant bonuses don't match the physical board game.
**Why it happens:** Values were entered manually and never cross-checked against a reference.
**How to avoid:** Compare every data file value against the rulebook and/or a reference implementation (npow/brass-birmingham is cited in the code).
**Warning signs:** Comments like "this could vary by player count" (seen in merchants.ts:55).

### Pitfall 4: ERA-specific rule omissions
**What goes wrong:** A rule applies differently in Canal vs Rail era, but only one era is tested.
**Why it happens:** Most tests default to Canal era setup.
**How to avoid:** For each era-dependent rule, verify BOTH eras are tested.
**Warning signs:** Rules mentioning "during the Canal Era" or "during the Rail Era" with only one test.

### Pitfall 5: Audit scope creep into fixes
**What goes wrong:** Auditor starts fixing bugs found during the audit, mixing audit documentation with code changes.
**Why it happens:** Natural developer instinct to fix what you see.
**How to avoid:** Strict discipline -- audit output is markdown only. Zero code changes. Capture fix details in notes column for the subsequent fix phase.

## Open Questions

1. **Merchant tile specific icons per merchant**
   - What we know: The rules say merchants feature specific industry icons, but the current `merchants.ts` gives all merchants `['cotton', 'manufacturer', 'pottery']`
   - What's unclear: Whether the physical game actually differentiates merchant tile icons (some merchants may only accept certain industries)
   - Recommendation: Verify during data layer audit (Plan 01) by checking BGG or reference implementation

2. **Merchant VP bonus values**
   - What we know: Code has `value: 2` for both Nottingham and Shrewsbury with a comment "this could vary by player count"
   - What's unclear: Whether VP bonuses are fixed or vary by merchant tile drawn
   - Recommendation: Verify during data layer audit against physical game reference

3. **Farm Brewery connection model**
   - What we know: Board.ts models farm breweries as separate cities with connections to Cannock/Walsall and Kidderminster/Worcester
   - What's unclear: The rules say "A Link tile placed between Kidderminster and Worcester also connects both locations to the Farm Brewery to their left. A second Link tile is not required; nor may it be placed there." This implies the farm brewery connection is implicit, not a separate link
   - Recommendation: Verify during network audit (Plan 04) whether the connection model correctly handles this special case
